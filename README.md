# Telegram ИИ-бот для существующего Render Web Service

Готовая версия проекта на Python 3.11: Groq, PostgreSQL, защищённый webhook, меню, память, поиск при наличии Tavily, текущая погода Open-Meteo и математические графики.

**Состояние проверки:** локальные автоматические тесты используют настоящую временную PostgreSQL и подменяют Telegram/Groq/погодные/поисковые API. Docker-образ собирается. Действующий Render-сервис не обновлялся; реальные ключи и внешняя база в этой задаче отсутствовали. Наличие моделей и текущие бесплатные квоты ещё нужно подтвердить на вашем аккаунте. План безопасного обновления и отката: [DEPLOYMENT.md](DEPLOYMENT.md). См. [RESEARCH.md](RESEARCH.md) и [AUDIT.md](AUDIT.md).

## Что скачать и загрузить

1. Скачайте ZIP проекта и распакуйте его в отдельную папку, например `C:\telegram-ai-bot-modernized`.
2. Сохраните старый проект и резервную копию SQLite отдельно. Не удаляйте старую базу.
3. Откройте существующий репозиторий `feedpremix-ship-it/telegram-ai-bot` на GitHub. Загрузите **всё содержимое распакованной папки**, сохраняя папки `assistant`, `scripts`, `tests`. Одной замены `bot.py` недостаточно.
4. В репозитории должны появиться `bot.py`, `assistant/`, `requirements.txt`, `requirements-dev.txt`, `Dockerfile`, `.dockerignore`, `.gitignore`, `.env.example`, `pytest.ini`, тесты и инструкции. Не загружайте настоящий `.env`, SQLite, ZIP или ключи.
5. Сохраните изменения в ветку, которую уже использует существующий Render-сервис. Если включён Auto-Deploy, загрузка запускает развёртывание: сначала подготовьте переменные, описанные ниже, либо временно отключите Auto-Deploy.

ZIP не содержит ключей, старой базы и каталога `.git`.

## Внешняя база: единственное необходимое новое подключение

Нужна внешняя PostgreSQL с TLS и прямыми соединениями. Новую базу на платном тарифе не создавайте. Подходящие кандидаты — Neon Free или Supabase Free, **только после проверки текущих бесплатных условий, отсутствия обязательной оплаты/карты и срока жизни проекта в их панели**. Конкретные условия из этой среды проверить не удалось; сравнение и контрольный список находятся в RESEARCH.md.

1. В панели выбранного провайдера выберите именно Free, регион рядом с Render и создайте PostgreSQL-проект без включения платных опций.
2. Скопируйте **direct connection string**, заменив пароль в самой панели/Environment. Не используйте transaction pooler и адреса вида `*-pooler.*`. Прямой адрес Supabase может требовать IPv6; если Render не соединяется, выберите подходящий прямой endpoint у другого бесплатного провайдера. Session pooler допускайте только если провайдер явно гарантирует сохранение сессии и session advisory locks; эта комбинация здесь не проверялась.
3. Добавьте `DATABASE_URL` в Render Environment. Пример формата: `postgresql://USER:PASSWORD@HOST/DB?sslmode=require`. Не вставляйте секреты в GitHub или чат. Специальные символы пароля должны быть URL-encoded: используйте готовую строку из панели, а не собирайте её вручную.
4. Схема создаётся автоматически. Для работы нужно не менее `WORKERS + 3` доступных соединений (по умолчанию максимум 5). Используется отдельная PostgreSQL-сессия для запрета второго экземпляра.
5. Сделайте резервное копирование доступным способом провайдера. Память переживает перезапуск приложения, но не удаление/истечение проекта базы.

Новая версия **не переключается молча на SQLite**, если PostgreSQL недоступна: запуск завершается с безопасной ошибкой, webhook возвращает 503 до готовности.

## Переменные Render Environment

Откройте **существующий** сервис → Environment. Сохраните имеющиеся значения токена Telegram и ключа Groq; не меняйте самого бота.

| Имя | Что указать |
|---|---|
| `TELEGRAM_TOKEN` | Ваш существующий токен BotFather |
| `GROQ_API_KEYS` | Существующий ключ Groq; используется первый непустой ключ, остальные не вращаются для обхода квот |
| `DATABASE_URL` | Прямая внешняя PostgreSQL-строка с `sslmode=require` |
| `WEBHOOK_URL` | `https://АДРЕС-ВАШЕГО-СУЩЕСТВУЮЩЕГО-СЕРВИСА.onrender.com/webhook` |
| `WEBHOOK_SECRET` | Новый случайный секрет из команды ниже; не публикуйте его |
| `GROQ_MODELS` | `openai/gpt-oss-120b,openai/gpt-oss-20b` — кандидаты, проверяемые через `/models` при запуске |
| `ADMIN_USER_IDS` | Ваш числовой Telegram user ID; только эти ID видят `/stats` |
| `ALLOWED_USER_IDS` | Необязательно: ID допущенных пользователей через запятую; пусто — все личные чаты |
| `TAVILY_API_KEY` | Необязательно: ключ бесплатного Tavily, если доступен в вашем аккаунте; без него поиск честно сообщает об отсутствии подключения |
| `MPLCONFIGDIR` | `/tmp/matplotlib` для Python runtime; в Docker уже задано |
| `WORKERS` | `2` (допустимо 1–4) |

Сгенерировать секрет на Windows при установленном Python:

```powershell
py -3.11 -c "import secrets; print(secrets.token_urlsafe(48))"
```

Секрет также можно сгенерировать в локальной доверенной Python-среде той же командой `python -c "import secrets; print(secrets.token_urlsafe(48))"`. Результат вставляйте только в Render Environment. Путь `/webhook` не должен содержать токен бота.

`PORT` обычно предоставляет Render — не заменяйте его своим значением без необходимости. Старые `MEMORY_DB`, `AUTO_SEARCH`, `STAGGER_SECONDS`, `MAX_HISTORY`, `DEFAULT_CITY`, `DEFAULT_COUNTRY`, `SEARCH_DEPTH`, `SYSTEM_PROMPT` не управляют новой версией. Язык/инструменты выбираются по смыслу запроса, неоднозначные города уточняются. Старый `ALLOWED_USER_IDS` сохранён. Старый лимит ответа 700 символов удалён.

## Обновление существующего Render-сервиса

1. Откройте ваш существующий Web Service. Не нажимайте New Web Service и не создавайте Blueprint по `render.yaml`: этот файл — только справочный образец настроек.
2. Для Docker runtime оставьте запуск по `Dockerfile`; Docker Command должен быть пустым либо `python bot.py`.
3. Если существующий runtime — Python, используйте Python 3.11, Build Command `pip install -r requirements.txt` и Start Command `python bot.py`. Сохраните существующие команды, если они уже выполняют эти действия и не устанавливают старые зависимости.
4. Установите Health Check Path `/healthz`. Проверьте выбранный тариф Free и один экземпляр приложения. Rolling deploy может временно не пройти singleton-lock, пока старый экземпляр не остановлен: остановите старый запуск и повторите deploy; не увеличивайте число экземпляров.
5. После сохранения Environment и загрузки файлов нажмите **Manual Deploy → Deploy latest commit**. Не включайте платные диски, платную базу или платный LLM-тариф.
6. Дождитесь строки `ready mode=webhook workers=2` в Render Logs. Она означает запуск и успешную проверку списка моделей, но ещё не успешный диалог с ИИ. Если есть `startup_failed`, проверьте Environment, прямой адрес PostgreSQL, TLS, доступность базы и моделей. Ошибки специально не печатают URI и ключи.
7. Откройте `https://АДРЕС-СЕРВИСА.onrender.com/healthz`: ожидается `{"status":"ok"}`. При проблеме — 503. Корневой `/` также поддерживает проверку здоровья, без искусственных периодических запросов.
8. Не запускайте вторую polling-копию бота на компьютере. Домашний компьютер после развёртывания не нужен.

При каждом старте сохраняется webhook с секретом, без сброса накопленных Telegram-обновлений. HTTP 200 отправляется после успешного сохранения обновления в PostgreSQL. Ошибка базы/переполнение очереди → 503, Telegram может повторить доставку. Одна входящая webhook-связь снижает риск перестановки доставки.

## Как проверить бота вручную

1. Напишите `/start`: должны появиться шесть кнопок меню.
2. Отправьте «Запомни: мой любимый цвет зелёный», затем «Какой мой любимый цвет?». Ответ должен учитывать предыдущий текст.
3. Выполните Manual Deploy ещё раз, дождитесь готовности и снова спросите про цвет. Это проверяет именно вашу внешнюю память после перезапуска.
4. Нажмите «🧹 Очистить историю», затем спросите про цвет. Бот должен не знать его. «💬 Новый диалог» тоже удаляет текущий контекст: архива старых диалогов в этой версии нет.
5. Отключите память через «🧠 Память». Новые реплики не должны сохраняться как контекст. Последний запрос и ответ временно сохраняются для доставки/повтора; `/clear` удаляет их.
6. Напишите «Переведи на английский: сегодня хорошая погода». Должен получиться перевод, а не погодная карточка.
7. Попросите текущую погоду с городом и страной; при неоднозначном названии бот должен запросить уточнение. Прогноз на будущие дни не реализован: инструмент получает только текущие погодные данные.
8. Напишите «Построй график sin(x) от -6 до 6», затем «Построй столбчатую диаграмму: А 10, Б 20». Должны прийти PNG-графики. Исходные значения модель может интерпретировать неверно — проверяйте подписи.
9. Попросите обычное объяснение: URL не должны появиться. Затем явно напишите «Дай ссылку на официальную документацию Groq»: ссылки разрешены. Их существование/содержимое автоматически не проверяются; не считайте ссылку подтверждённой только по ответу модели.
10. Проверьте два разных Telegram-аккаунта: их история должна быть независимой. Поддерживаются только личные чаты, не группы.
11. С администраторского аккаунта выполните `/stats`. Проверяется число попыток, ошибок, известных токенов и неопределённых попыток; токены/ключи других пользователей не показываются.

Не создавайте искусственную нагрузку на реальные Telegram/Groq и не отправляйте личные данные для проверки.

## Квоты и скорость

Локальные значения по умолчанию — **защитные настройки проекта, а не подтверждённые бесплатные квоты Groq**:

- `DAILY_REQUEST_LIMIT=900` API-попыток в UTC-сутки, включая неудачные и вызовы для инструментов.
- `DAILY_TOKEN_LIMIT=180000` консервативно зарезервированных токенов в UTC-сутки.
- `MINUTE_TOKEN_LIMIT=30000` зарезервированных токенов за последние 60 секунд и максимум 15 API-попыток за минуту.
- `USER_DAILY_LIMIT=50` пользовательских запросов в UTC-сутки и пауза 2 секунды между запросами пользователя.
- `MAX_OUTPUT_TOKENS=1200`, `CONTEXT_CHARS=12000`, не больше 30 последних сообщений контекста.
- `QUEUE_SIZE=200`, `WORKERS=2`. Графики строятся по одному на весь процесс.

Перед каждым API-запросом сохраняется резерв: размер JSON в UTF-8 байтах плюс максимум выходных токенов. Резерв намеренно завышен и не возвращается после ошибок. Это ограничивает бесплатный расход даже при сбое после отправки запроса. Фактические `usage.total_tokens` учитываются отдельно. С такой защитой токенный бюджет может закончиться намного раньше 900 запросов.

Инструмент требует обычно **два** LLM-вызова: выбрать действие, затем объяснить результат. Одновременных обращений к резервным моделям нет. При 429 соблюдается `Retry-After` (секунды или HTTP-дата), блокируется весь Groq-клиент. При тайм-ауте/5xx автоповтор не выполняется: неизвестно, израсходовал ли провайдер квоту. Резервная модель используется только при 404/подтверждённом удалении модели. Если два человека нажали повтор, запросы всё равно идут последовательно по каждому пользователю.

Повтор после ошибки доставки использует сохранённый текст без нового LLM-вызова; частично доставленные фрагменты могут повториться. Если изображение не доставлено, его нужно запросить заново. После ошибки самого LLM ручная кнопка повтора делает новую API-попытку и расходует квоту.

Менять локальные лимиты следует только после просмотра ваших настоящих RPM/RPD/TPM/TPD. Ключи нескольких аккаунтов не используются для обхода ограничений. Платные услуги и искусственный keep-alive не подключены.

## Надёжность и границы

PostgreSQL хранит очередь до подтверждения webhook. Разные пользователи могут обрабатываться параллельно; уже принятые обновления одного пользователя идут по `update_id`, а следующий запрос ждёт завершения предыдущего. Повторный `update_id` не вызывает ещё один LLM-запрос в пределах сохранённого журнала (7 дней).

Это **не exactly-once**: Telegram, Groq и PostgreSQL не участвуют в общей транзакции. При аварии в ходе обработки запись помечается `interrupted` на следующем старте и не запускается снова автоматически, чтобы не удваивать расход. Пользователь должен прислать запрос ещё раз; ответ мог быть частично доставлен. Незавершённый расход виден в `/stats` как неопределённый. Принятые, но ещё не начатые запросы сохраняются и обрабатываются после старта. Встроенной гарантии доставки всех запросов на Free нет.

Очередь хранит полный текст ожидающего обновления до обработки; после завершения/ошибки/прерывания payload удаляется, ID дедупликации сохраняется 7 дней. Журнал API хранится 30 дней без текстов запросов и ключей. Текущая история и последний запрос живут до очистки/отключения памяти; `/clear` удаляет их из рабочей базы, но не из резервных копий провайдера. Общая статистика не содержит текстов. Рост количества пользователей всё равно требует контроля размера базы и её бесплатной квоты.

Ожидание базы и холодный старт Render могут задержать ответ. При постоянном трафике сервис может исчерпать бесплатные часы; Free не гарантирует SLA. Облачная БД также может засыпать/приостанавливаться. Никакой обход сна не используется.

Графики используют собственный ограниченный AST-интерпретатор (без `eval`/`exec`) и отдельный процесс с CPU/временным пределом; выражения ограничены, 400 точек, максимум 20 столбцов/долей. Изображения хранятся в памяти и освобождаются после отправки. Формулы: `x`, `pi`, `e`, `+ - * / **`, `sin`, `cos`, `tan`, `sqrt`, `log`, `log10`, `exp`, `fabs`. Python-код, импорты и доступ к атрибутам запрещены. Построение PNG проверено внутри контейнера с лимитом 512 MiB; это не нагрузочный тест Render.

Open-Meteo возвращает модельные текущие погодные данные с указанием времени/единиц; это не гарантированное измерение на месте. Бесплатное некоммерческое использование и обязательную атрибуцию проверьте по актуальным условиям; атрибуция передаётся модели. Поиск не работает без опционального Tavily; бот не имитирует просмотр интернета. Поддержка нейросетевых изображений не заявлена.

## Перенос старой SQLite

Не удаляйте и не коммитьте базу. Если нет сохранённого файла, данные на уже перезапущенном Render Free восстановить из кода нельзя.

1. Получите согласованную SQLite backup-копию из работающего старого окружения через SQLite backup API; обычное копирование только `.db` при наличии WAL может потерять данные. Пример команды на машине, где доступна старая база:

```powershell
py -3.11 -c "import sqlite3; a=sqlite3.connect('data/bot.db'); b=sqlite3.connect('backup.db'); a.backup(b); b.close(); a.close()"
```

2. Сохраните `backup.db` отдельно от проекта и остановите новую/старую копии бота на время переноса. Не делайте новый deploy до завершения переноса.
3. Подготовьте локальное окружение по командам ниже и локальный `.env` с `DATABASE_URL`. Укажите абсолютный путь к вашей копии:

```powershell
.\.venv\Scripts\python.exe scripts\migrate_sqlite.py "C:\backup\backup.db"
```

4. Инструмент перенесёт не более 30 последних сообщений личного чата в пределах контекста, сохранит отметку миграции и не изменит SQLite. Повтор того же файла ничего не дублирует. Если в целевой базе уже есть история, операция отменяется целиком. Старые профили произвольного формата и статистика квот не импортируются: это явно другая схема. Групповые chat ID не переносятся.
5. Запустите существующий Render-сервис и проверьте память. Только после проверки решайте, как архивировать старую копию.

## Локальная разработка на Windows 10

Нужен установленный Python 3.11. Компьютер не обязан быть включён после развёртывания на Render.

```powershell
cd C:\telegram-ai-bot-modernized
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
notepad .env
```

Заполните `.env` значениями безопасно и оставьте `WEBHOOK_URL` пустым только для локального polling. **Не запускайте локальный polling одновременно с рабочим webhook**: это удалит webhook существующего бота. Для обычной разработки запускайте только тесты:

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests\test_core.py
```

Для согласованного ручного локального запуска при остановленном Render:

```powershell
.\.venv\Scripts\python.exe bot.py
```

## Тесты с отдельной PostgreSQL

Никогда не задавайте production `DATABASE_URL` как `TEST_DATABASE_URL`: тесты очищают таблицы `assistant_*`. Они нужны только в одноразовой базе.

Пример Docker на локальной машине с установленным Docker, loopback-доступом и временной тестовой БД:

```powershell
docker run --name telegram-bot-test-db --rm -d -e POSTGRES_HOST_AUTH_METHOD=trust -p 127.0.0.1:15432:5432 postgres:16-alpine
$env:TEST_DATABASE_URL="postgresql://postgres@127.0.0.1:15432/postgres"
.\.venv\Scripts\python.exe -m pytest -q
docker stop telegram-bot-test-db
Remove-Item Env:TEST_DATABASE_URL
```

Дождитесь готовности PostgreSQL перед тестами (`docker logs telegram-bot-test-db`). `trust` предназначен только для одноразовой тестовой БД на loopback, не для облачной базы.

Без `TEST_DATABASE_URL` интеграционные тесты пропускаются — это не проверка PostgreSQL. См. `VALIDATION.md` для фактически выполненных проверок и ограничений.
