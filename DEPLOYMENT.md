## PostgreSQL без платной подписки

Предпочтение: отдельный PostgreSQL-проект Neon на Free при подтверждении актуальных условий. Supabase допустим при доступном direct endpoint. От аккаунта БД требуется: прямой TLS endpoint, постоянное хранилище, минимум 5 доступных сессий, отсутствие transaction pooler. Не включать карту, autoscaling сверх Free, платные backups или upgrade. Если предлагается только оплачиваемая опция — остановиться.

Параметры приложения подготовлены в `.env.example`. Нужен `DATABASE_URL` из панели провайдера, а не введённый в код пароль. Внешнее TLS-соединение проверяет цепочку CA и имя хоста. Роль приложения должна владеть создаваемыми `assistant_*` таблицами (или иметь BYPASSRLS). Для Supabase включён RLS без публичных политик на всех таблицах: anon/authenticated API-доступ не предоставляется. Никогда не выставляйте service-role пароль пользователям Telegram. Желательно отдельная БД/проект, не общая с чужими приложениями.

Read-only проверка из доверенного окружения, где DATABASE_URL уже задан безопасно:

```bash
python scripts/check_database.py
```

Команда не создаёт таблицы, не регистрирует webhook и не выводит URI. В Render не запускалась: доступа нет. Создание схемы делает бот при запуске. SQLite backup переносится отдельно по README с остановленными экземплярами бота.

## Предварительная проверка без вмешательства в действующего бота

1. Проверить владельца, текущий branch и deployed commit в Render → существующий сервис → Settings/Events. Сохранить их и текущие Build/Start Command, health path и имена Environment-переменных. Значения секретов не помещать в GitHub.
2. Создать/подключить только бесплатный PostgreSQL-проект. Проверить условия Free в панели, TCP-доступ из Render, TLS read-only командой выше.
3. До любых изменений рабочей среды подготовить backup старой SQLite через backup API, экспорт/backup новой PostgreSQL и безопасно сохранить текущую конфигурацию. Если исходные данные уже пропали на эфемерном диске, не обещать восстановление.
4. Провести реальную API-проверку Groq: `/models`, один чат и один tool-call, сверить организационные RPM/RPD/TPM/TPD. Сервис сейчас этого не проверял. Установить локальные лимиты не выше подтверждённых бесплатных квот.
5. Проверить версию приложения с отдельным тестовым Telegram-ботом и отдельной БД локально. Не запускать `bot.py` с рабочим токеном для теста: он меняет webhook. Новый Render-сервис не нужен.
6. Только после проверок принимать решение о merge. Если Render Auto-Deploy включён, перед merge его отключить в существующем сервисе → Settings → Build & Deploy → Auto-Deploy. Не менять рабочую ветку сервиса на review-ветку.

## Окно обновления (после отдельного разрешения)

1. Зафиксировать фактический предыдущий deployed SHA и способ возврата к нему. Остановить старый процесс в согласованное окно, чтобы не конфликтовали обработчики и singleton lock.
2. Перенести backup SQLite в подготовленную PostgreSQL через `scripts/migrate_sqlite.py`, пока бот остановлен. Проверить число пользователей. Сохранить исходный backup.
3. Добавить только недостающие параметры в Render Environment: DATABASE_URL, WEBHOOK_SECRET, корректный WEBHOOK_URL; обновить GROQ_MODELS только после live проверки. Существующие TELEGRAM_TOKEN/GROQ_API_KEYS не ротировать. Новый webhook secret требует безопасного ввода/согласования; в этой задаче он не создавался и не менялся.
4. Проверить Free plan, один экземпляр, Dockerfile либо `pip install -r requirements.txt` / `python bot.py` для Python 3.11. Health path `/healthz`.
5. Слить проверенный PR в main и вручную развернуть проверенный commit существующего сервиса. Не включать искусственный keep-alive.
6. Проверить ready, HTTP health 200, Telegram /start, вопрос-ответ, память после повторного запуска, /clear, два независимых пользователя, график, отсутствие публичных URL без просьбы. Проверить backlog и /stats, ошибки/расход Groq. При провале остановить обновление и перейти к откату.

## Откат

1. Остановить новую копию; не допускать двух процессов с одним Telegram-токеном.
2. В Render открыть Events/Deploys и выполнить Rollback к сохранённому фактическому deployed commit (если функция доступна на текущем тарифе). Иначе развернуть отдельный revert commit после review; не выполнять force push/reset main.
3. Восстановить сохранённые Build/Start/health настройки и прежний webhook-режим. Если предыдущая версия не проверяла webhook secret, явно вернуть предыдущую регистрацию webhook, чтобы не осталось неопределённого состояния. Не использовать `drop_pending_updates=True`.
4. Не удалять PostgreSQL и новые данные. Старая версия может не уметь их читать. Не заменять новую БД старым backup: это потеряет новые диалоги.
5. Если старая версия использовала локальную SQLite, её диск/файл после deploy может отсутствовать. Восстановить согласованную backup-копию отдельно; rollback кода сам по себе данные не возвращает. Учесть новые сообщения, поступившие после миграции, перед возвратом к SQLite.
6. Проверить ответ Telegram. Не повторять неопределённые LLM-запросы автоматически. Обновление считать завершённым только после проверки поведения и сохранности данных.
